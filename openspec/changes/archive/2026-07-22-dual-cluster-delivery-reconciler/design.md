# Design: dual-cluster-delivery-reconciler

## Context

`dual-deployment-operator` renders one artifact per operator (Helm chart or kustomize source) twice — once for the seed/host cluster, once for the shoot/remote cluster — applies typed Go transformations to each render, and applies each render directly to its target Kubernetes API. See [`docs/design.md`](../../../docs/design.md) (r7) and [`docs/implementation.md`](../../../docs/implementation.md) for the full architecture.

**Current state.** Phases 0–3 are complete and archived: operator scaffold + CRD types (`api/v1alpha1`), source renderers (`internal/source`, Helm + kustomize, two-render), the manifest parser (`internal/manifest`, origin tagging), and the typed transformations (`internal/transform`: `patch`, `rewriteWebhookURL`, `filterKinds`). The reconciler in `internal/controller/dualdeploymentoperator_controller.go` is a **no-op stub** — it fetches the CR and returns. The CRD Status already defines `ResourceStatus`, `HealthState`, `DeletionPolicy` (renamed to `RetentionPolicy` by this change — see Decisions), and `RemoteKubeconfigRef`, so the delivery/status shape exists but is unused.

**This change** implements Phases 5 (Delivery) and 6 (Reconciler): the dual-cluster direct-apply mechanism and the reconcile loop that ties rendering, transformation, and delivery together.

**Constraints.**
- **r7 webhook-injector coexistence**: the operator applies `Validating/MutatingWebhookConfiguration` and conversion-webhook CRDs to the shoot but must never own the `caBundle` field — the webhook-injector (target patch mode) owns it exclusively via SSA disjoint-field ownership.
- **Two clients per CR**: host (in-cluster, the manager's own client) and shoot (`rest.Config` built from a Gardener token-requestor Secret's `token` + `bundle.crt` plus `spec.remoteAccess.server`; token rotates, so the client is rebuilt each reconcile).
- **Per-shoot topology**: one operator instance per shoot control-plane namespace.
- **TDD is mandatory** (project AGENTS.md + `sdd-plus-superpowers`): RED→GREEN→REFACTOR per task via `subagent-driven-development`.

**Stakeholders.** The five remote operators (metal-operator, boot-operator, argora-operator, khalkeon, ipam-capi) migrating off the pre-render-and-commit model; the webhook-injector (shares WebhookConfig/CRD objects on the shoot); Gardener (supplies the shoot token-requestor Secret with `token` + `bundle.crt`).

## Goals / Non-Goals

**Goals:**
- Implement `internal/deliver`: a stateless server-side-apply `Applier` with per-resource health computation and caBundle-safe apply.
- Implement `internal/clients`: host (in-cluster) and shoot (token+CA-from-Secret) client factories.
- Rewire the reconciler to: render twice → transform each render → sort each render (fixed intra-render kind-priority) → apply each render to its target cluster in consumer-chosen `applyOrder` → prune orphans → report per-resource + aggregate status → requeue for drift correction.
- Add a consumer-configurable `spec.applyOrder` (`HostFirst`/`RemoteFirst`, default `RemoteFirst`) governing cross-render apply sequence; deletion and prune run the reverse.
- Prune resources that vanish from a render between reconciles (applied-set tracking), respecting `retentionPolicy.crds=Retain`.
- Guarantee the operator never becomes the SSA field manager of `caBundle` (leaf-only, unconditional strip), preventing webhook-outage windows.
- Handle CR deletion via a finalizer that tears down remote resources (no ownerRef cascade across clusters) before the CR is removed.

**Non-Goals:**
- The webhook-injector itself, its cert lifecycle, or its target patch mode (separate component).
- Gardener token/CA rotation (we only consume a Secret Gardener maintains).
- Equivalence tests vs. the legacy chart output (Phase 7), the deployment chart (Phase 8), or the validating admission webhook (Phase 9).
- Intra-render kind ordering as a consumer knob — the intra-render order is a fixed built-in; only the cluster sequence is configurable.
- Making the `caBundle`-strip helper stamp the injector's `--target-label` — labeling is the `patch` transformation's job (already shipped in Phase 3).

## Capabilities

**New Capabilities:**
- `resource-delivery` — server-side-apply delivery of a manifest set to a target cluster: SSA with `ForceOwnership`, leaf-only unconditional `caBundle` stripping on WebhookConfig/CRD, GET-after-apply per-resource health (WebhookConfig health is existence-only — the operator does not grade caBundle, which it does not own), idempotent delete, and fixed intra-render kind-priority ordering.
- `cluster-clients` — construction of the host (in-cluster) and shoot (`rest.Config` from a token-requestor Secret's token+CA plus `server`) `client.Client` instances used for delivery.
- `reconcile-loop` — the end-to-end reconcile: render×2 → transform → sort → apply per `applyOrder` → prune → status; finalizer-gated deletion; periodic drift-correction requeue.

**Modified Capabilities:**
- `crd-types` — add `spec.applyOrder` (enum `HostFirst`/`RemoteFirst`, default `RemoteFirst`); rename `spec.deletionPolicy` → `spec.retentionPolicy` (type `DeletionPolicy` → `RetentionPolicy`), keeping the `.crds` sub-field.
- `noop-reconciler` — superseded: the no-op reconcile behavior is replaced by `reconcile-loop`.

## Decisions

**Decision: package layout — applier-per-cluster + thin reconciler**
- Chosen: `internal/deliver` (stateless `SSAApplier` + pure `order.go`/`health.go`), `internal/clients` (two factories), reconciler orchestrates.
- Reason: clean unit boundaries; the applier is testable against a fake client with no reconciler; ordering/health/strip are pure functions; matches documented Phase 5/6 structure.
- Alternatives considered: a fat `Deliverer` facade (god-object, couples `deliver` to the CR type, sub-behaviors not independently testable — rejected); reconciler-embedded delivery with no `deliver` package (controller balloons, not testable without the harness — rejected).

**Decision: consumer-specified cross-render sequencing (`spec.applyOrder`)**
- Chosen: enum `HostFirst`/`RemoteFirst`, default `RemoteFirst`; deletion/prune reverse it. Both renders always applied (best-effort sequencing, not a hard gate).
- Reason: CRDs/RBAC/webhooks live on the remote and should exist before the host controller starts; on teardown the controller should stop before its CRDs are removed. Not gating avoids coupling the two clusters' convergence (consistent with continue-on-error).
- Alternatives considered: fixed built-in order with no knob (docs' original — less flexible per operator); gating the second render on the first fully succeeding (couples clusters, a transient remote hiccup blocks host convergence — rejected); consumer-ordered *kinds* within a render (over-configuration; the intra-render dependency order Namespace→CRD→RBAC→workload→webhook is invariant — rejected).

**Decision: rename `deletionPolicy` → `retentionPolicy` (keep `.crds`)**
- Chosen: rename the spec field `deletionPolicy` to `retentionPolicy` and the Go type `DeletionPolicy` to `RetentionPolicy`, keeping the single `.crds` sub-field (enum `Retain`/`Delete`, default `Retain`) and the `+kubebuilder:default={crds:Retain}` marker. Use site reads `retentionPolicy: {crds: Retain}`.
- Reason: the field protects only CRDs (the sole kind whose deletion cascades to user data); every other resource is always pruned/deleted. "deletionPolicy" over-promises broad deletion control it does not have. "retentionPolicy" accurately frames it as *what to keep on removal*, and the grouped struct leaves room for future retain-vs-delete knobs (`retentionPolicy.namespaces`, `retentionPolicy.pvcs`) without another flat field.
- Applies to the `crd-types` capability. Executed during apply: edit `api/v1alpha1/dualdeploymentoperator_types.go`, run `make manifests generate` (regenerates CRD base + zz_generated deepcopy), no reconciler code depends on it yet.
- Alternatives considered: flat `crdPolicy` (honest but loses grouping/extensibility — viable if CRDs stay the only knob; not chosen to preserve the group); keep `deletionPolicy` + document scope (doesn't fix the top-level over-promise — rejected); per-kind retention rules map (speculative generality for one real case — rejected, YAGNI).

**Decision: shoot access via token-requestor Secret, not a kubeconfig blob (`spec.remoteKubeconfig` → `spec.remoteAccess`)**
- Chosen: rename `spec.remoteKubeconfig` → `spec.remoteAccess` (Go type `RemoteKubeconfigRef` → `RemoteAccessRef`). Fields: `secretName` (required), `server` (required), `tokenKey` (optional, default `token`), `caKey` (optional, default `bundle.crt`). The operator reads the bearer token and CA bundle from the named Secret keys and builds the shoot `rest.Config` directly as `{Host: server, BearerToken: <token>, CAData: <caBundle>}`, rebuilt per reconcile.
- Reason: chart research (metal-operator-remote, boot-operator-remote) confirmed the credential Gardener actually produces via the token-requestor pattern is a Secret with **`token` + `bundle.crt`**, not a self-contained kubeconfig — Gardener injects and rotates both (Secret carries `serviceaccount.resources.gardener.cloud/*` + `inject-ca-bundle: "true"`). Consuming this shape directly matches what all five operators' charts already receive today, so **no chart change is required** — the token-requestor Secret already exists. Rebuild-per-reconcile picks up token/CA rotation. The name `remoteAccess` reflects reality (token+CA, not a kubeconfig), consistent with the `retentionPolicy` rename rationale.
- `server` is **required with no derived default**: the operator Pod runs in the seed, so it cannot infer the shoot API server address from its own environment. The value is supplied per CR (the wrapper charts already carry it as `KUBERNETES_SERVICE_HOST` / the shoot apiserver Service address `kube-apiserver.<shoot-cp-ns>.svc.cluster.local:443`); the chart stamps it into the CR from the same value.
- `tokenKey`/`caKey` are configurable but default to Gardener's conventions, so a standard Secret needs neither set.
- Applies to `crd-types` (field rename + `RemoteAccessRef`) and `cluster-clients` (shoot factory builds `rest.Config` from token+CA+server, not `RESTConfigFromKubeConfig`). Executed during apply.
- Alternatives considered: inline-kubeconfig Secret (Gardener injects the token into `users[].user.token`, keep `RESTConfigFromKubeConfig`) — rejected because its CA is a **static** Helm value (`.Values.remote.ca`, no `inject-ca-bundle`), so it goes stale if the shoot CA rotates, and only the `metal-token-rotate` sidecar uses that shape today (would require a chart-template change); kubeconfig-file-in-ConfigMap + tokenFile mount (metal's main pattern) — rejected because it targets a Pod consuming its own shoot access via a mounted file, not an operator holding many programmatic clients; deriving `server` from the operator's namespace — rejected (operator is seed-deployed; the in-cluster address is a Gardener seed-topology assumption, not a Kubernetes truth, and the fleet already treats the URL as explicit config).
- Chosen: diff previous `status.HostResources`/`status.RemoteResources` (identity key `group/kind/namespace/name` — version-independent, see below) against the new render; delete orphans by direct `Get`+`Delete` in reverse-delete order; skip CRDs under `retentionPolicy.crds=Retain`. Status is written after apply+prune, so failed prunes stay tracked and self-heal next reconcile.
- Reason: this is the mechanism the two closest analogues use. **GRM** (gardener-resource-manager — the very thing r7 replaces) builds an index from `ManagedResource.status.resources` and deletes anything not in the new desired set via `Get`+`Delete`, needing **no `list` RBAC** on the target ([reconciler.go#L197-198, L514-515, L564](https://github.com/gardener/gardener/blob/9ec843ed9b86696134f07ff957ce539a396ac42e/pkg/resourcemanager/controller/managedresource/reconciler.go#L197-L198)). **Flux kustomize-controller** snapshots `.status.inventory`, `inventory.Diff(old,new)`, deletes stale by GVK+ns+name, also **`get`+`delete` only** ([kustomization_controller.go#L341-344, L448-449](https://github.com/fluxcd/kustomize-controller/blob/3d2769f3f79b52926b8ed1a32703f034dc70be9a/internal/controller/kustomization_controller.go#L341-L344)). Both match our approach. Only **ArgoCD** uses the live-listing alternative (watch/list all cluster objects, attribute by `argocd.argoproj.io/tracking-id`), and it consequently requires **cluster-admin (`*/*/*`)** on every target — unacceptable RBAC blast radius on a data-bearing shoot.
- Trade-off (confirmed by Flux's own docs/source): status-diff's failure mode is **leaking** (if `status` is lost/cleared, the operator forgets what it applied → stale objects linger untracked but are not wrongly deleted). Live-listing's failure mode is **over-deletion** (a mis-scoped selector or label collision can sweep objects, including user CR data). For a data-bearing shoot, leak-safe beats resilient-but-dangerous.
- Ownership-label safety check (adopt from Flux): stamp a CR-identity label — key `dual-deployment-operator.cc.sap/owned-by`, value a fixed-length hash (first 16 hex of `sha256("<namespace>/<name>")`) of the owning CR — on applied objects and, at prune time, verify it on the fetched object before deleting (skip if it doesn't match). A hash, not a raw `<namespace>_<name>`, because a label value caps at 63 chars (a raw join can overflow, which would fail the apply) and the hash is injective across the ns/name boundary; it stays deterministic so it survives restarts/re-reconciles/same-name re-creation. This is free — we already `Get` the object — and guards against deleting something we didn't apply, without any `list` RBAC. (Flux does exactly this: prune candidates come from the status inventory, but a label-match gate precludes deleting non-owned objects — [ssa/manager_delete.go#L77-89](https://github.com/fluxcd/pkg/blob/c8dd701dd80aa97427fccded472ca1b3bac6d04a/ssa/manager_delete.go#L77-L89).) The same `owned-by` label is reused by the cluster-scoped conflict guard (see the "defensive cluster-scoped conflict guard" Decision).
- Identity key is **version-independent** (`group + kind + namespace + name`, not `apiVersion/...`): an API-group version bump (`v1beta1`→`v1`) should update the same logical object in place, not read as delete+recreate. `ResourceStatus` stores `APIVersion`, so the key derivation drops the version explicitly.
- Alternatives considered: no prune (orphans persist until CR deletion — leaves stale RBAC/webhooks; rejected); live-listing label-GC à la ArgoCD (needs broad `list`/`watch` — i.e. near-cluster-admin — on both clusters; over-deletion is the dangerous failure on a data-bearing shoot; rejected); label as *identity key* instead of GVK+ns+name (synthetic ID adds bookkeeping to re-derive an identity the object already has, and would wrongly treat a genuine rename as "same object"; rejected). A **hybrid** (status-diff primary + periodic label-scoped sweep to recover from status loss) is a noted v2 option, not v1.

**Decision: caBundle strip is leaf-only and unconditional**
- Chosen: `unstructured.RemoveNestedField(wh, "clientConfig", "caBundle")` on every apply, including the first; never remove the parent `clientConfig` or the webhook entry. A discriminating test asserts the operator's `managedFields` never lists a `caBundle` path.
- Invariant: the operator must **never become a field manager of `caBundle`**. SSA prunes a field only when an applier *owned it previously and omits it now*; omitting a never-owned field is a no-op (`ForceOwnership` does not change this). So the risk is not "omitting caBundle deletes it" — it is the *owned-then-omitted* transition. Because the rendered WebhookConfigs/CRDs frequently carry a `caBundle` field, a conditional strip ("only if present") or any single apply that submitted `caBundle` (even `""`) would enter it into the operator's `managedFields`; the next omit would then prune the injector's value, opening a webhook-outage window. The unconditional strip prevents ownership from ever being established. Ownership is server-side state in the shoot object's `metadata.managedFields` keyed by manager name, so the operator and injector co-own disjoint fields of the same shoot object as two independent clients.
- Leaf-only preserves the operator-owned `clientConfig.url`.
- Alternatives considered: strip the whole `clientConfig` when caBundle is its only key (would wipe operator-owned routing — rejected); strip conditionally only when present (leaves a first-apply ownership window — rejected).

**Decision: GET-after-apply health**
- Chosen: after SSA apply, one GET reads observed status; compute per-kind health (Deployment/StatefulSet replicas, CRD `Established`, else exists=Healthy). GET failure → `Unknown` (non-fatal).
- WebhookConfigurations are **not** special-cased and the operator does **not** inspect `caBundle`: it deliberately does not own that field (disjoint-field design), so grading its own health on caBundle would be inconsistent and would flap `Progressing` during the normal bootstrap window for a condition the operator cannot fix. WebhookConfigs report `Healthy` on existence; populating and observing caBundle is the injector's responsibility.
- Reason: the SSA apply response reflects desired spec, not observed status (`availableReplicas` absent), so health from the response alone is unreliable.
- Alternatives considered: health from the apply response only (cheaper, but wrong for workloads — rejected).

**Decision: continue-on-error, aggregate**
- Chosen: attempt every resource in a batch; per-resource failures set `Health=Degraded`+`Message`; reconcile returns a `kerrors.NewAggregate` → requeue with backoff. Render/transform/client-build errors are fatal to the reconcile (set `Ready=False` with a reason, requeue).
- Reason: one bad resource must not block the rest; maximizes convergence; matches the per-resource `ResourceStatus` in the CRD.
- Alternatives considered: fail-fast abort on first error (one transient conflict blocks all later resources — rejected).

**Decision: helpers in `internal/manifest`**
- Chosen: add `StripInternalAnnotations()` (removes the origin annotation before apply) and `ResourceStatus.AsManifest()` (rebuilds a minimal `manifest.Manifest` from status for deletion), placed to avoid an import cycle.
- Reason: keeps origin/annotation-key knowledge in one package rather than duplicated in `deliver`.
- Alternatives considered: put strip/convert in `internal/deliver` (duplicates the annotation key, `deliver` learns manifest internals — rejected).

**Decision: concurrency safety — no Helm-style lock; rely on framework serialization + optimistic concurrency + SSA + leader election**
- Chosen: no application-level lock. Four layers: (1) controller-runtime workqueue serializes reconciles per CR key (same CR never reconciled concurrently, by construction); (2) optimistic concurrency on the CR via `resourceVersion` (409 on `Status().Update` → requeue + re-read); (3) SSA `FieldOwner`+`ForceOwnership` on target objects (authoritative-manager; disjoint-field coexistence with the injector); (4) leader election (`--leader-elect`, already wired in `cmd/main.go`) so at most one operator instance is active cluster-wide.
- Reason: the framework already provides the per-object serialization Helm hand-builds with its status-as-lock. Unlike Helm, there is no stuck-`pending-*` failure mode — a crashed reconcile simply requeues; no lock to clear manually. Matches the `kubectl`/API-server model (per-object optimistic concurrency + SSA), not Helm's release lock.
- Deployment requirement: run with `--leader-elect=true`. Layers 2–3 are the safety net if leadership lapses (losing writer gets 409, not corruption).
- Replica count (community-aligned): `replicas: 1` + leader election is the recommended default for this low-load, per-shoot operator — matches cert-manager's default (`replicaCount: 1`; "in production set to 2 or 3… uses leader election"); prometheus-operator even runs single-replica without leader election on the rationale that a 15–30 s gap is tolerable. Replicas are active-passive **failover, not horizontal scale** — all CRs go to the single leader; the operator does not spread CRs across instances. `replicas: 2` is an optional HA upgrade, not a requirement.
- Leader election required even at `replicas: 1`: a rolling update transiently runs two pods (`maxSurge`), which would otherwise both reconcile. Set `LeaderElectionReleaseOnCancel: true` (currently commented in `cmd/main.go`) so the outgoing leader releases the lease on graceful shutdown → near-instant handoff instead of a ~15 s `LeaseDuration` wait. Layer-1 workqueue serialization is *per process*; leader election extends single-reconcile-per-CR *across pods* — complementary, not redundant.
- Sharding out of scope: distributing distinct CRs across active instances (controller sharding — `timebertt/kubernetes-controller-sharding`, or Alpha KEP-5866 server-side sharded watch, v1.36) is for extreme scale only; the per-shoot topology already partitions CRs across deployments.
- Alternatives considered: Helm-style status-as-lock on the CR (reinvents what controller-runtime already guarantees; adds a stuck-pending failure mode — rejected); no leader election (two replicas could reconcile the same CR concurrently — rejected). Evidence: Helm `errPending`/status lock ([action.go](https://github.com/helm/helm/blob/main/pkg/action/action.go), no auto-recovery); kubectl/API-server per-object optimistic concurrency + SSA conflicts ([SSA conflicts](https://kubernetes.io/docs/reference/using-api/server-side-apply/#conflicts)); kustomize has no concurrency control (stateless generator); active-passive HA + leader election is the controller-runtime/kubebuilder canonical pattern ([kubebuilder book](https://book.kubebuilder.io/); [controller-runtime#2836](https://github.com/kubernetes-sigs/controller-runtime/issues/2836)).

**Decision: shoot RBAC bootstrap via a minimal GRM ManagedResource (the operator SA cannot self-bootstrap its own apply permissions)**
- Chosen: a small, static, per-operator Gardener `ManagedResource` — applied by gardener-resource-manager (GRM), which is already effectively `cluster-admin` on the shoot — seeds exactly the shoot **ServiceAccount** the operator authenticates as, plus a **ClusterRole + ClusterRoleBinding** granting that SA broad *apply* rights (create/update/delete on the kinds the operator delivers: CRDs, ClusterRoles/Bindings, Roles/Bindings, ServiceAccounts, Validating/Mutating WebhookConfigurations, and the operator's additions). The operator then authenticates as that now-empowered SA (via its token-requestor Secret, `spec.remoteAccess`) and applies **everything else** — the bulk CRD/RBAC/webhook content and additions — directly via SSA.
- Reason: chart research confirmed that today GRM (privileged) performs the delivery-time apply, while the operator's token-requestor SA holds **only runtime domain permissions** — the existing `*-manager-role` ClusterRoles have **no `rbac.authorization.k8s.io` rules**, so that SA cannot create ClusterRoles/Bindings/SAs. Kubernetes privilege-escalation prevention also forbids an applier from creating a ClusterRole granting powers it does not already hold. Therefore the operator (authenticating as that SA) **cannot bootstrap its own apply permissions** — *something privileged must seed them first*. GRM is that privileged actor and already exists. Keeping a minimal bootstrap MR resolves the recursion cleanly: GRM creates only the ~30-line grant; the operator does the rest.
- Goal is NOT compromised: the "zero GRM / zero ManagedResource" goal targets the **runtime delivery path** — eliminating the ~30k lines of committed generated YAML, the `make build-` targets, and GRM as the ongoing delivery mechanism for CRDs/RBAC/webhooks. That path stays fully MR-free and GRM-free; the operator applies all content directly via SSA. The bootstrap MR is a **one-time, install-time** artifact (chart install / kustomization) that seeds a tiny static RBAC grant — it carries no generated content, never regenerates, does not drift, and is not part of the reconcile loop. It belongs to the same install-time, Gardener-provided category as the token-requestor Secret (also GRM/Gardener plumbing) — not the runtime delivery the design set out to replace. So: runtime = zero GRM (goal intact); install-time = one minimal GRM-seeded RBAC grant.
- Blast radius: the operator SA gets broad *apply* rights **scoped to the shoot**, not a raw cluster-admin client cert; the grant is static, small, auditable, and rarely changes. Bounded by the shoot.
- Two-principal model preserved conceptually: GRM = the privileged bootstrapper (seeds the grant, once); the operator = the everyday applier (uses the grant to deliver content). The content path is still MR-free; only the permission grant is via MR.
- Alternatives considered: operator authenticates as a **cluster-admin-bound SA** (e.g. GRM's own or a dedicated privileged SA) — rejected: puts full cluster-admin in the operator's hands (large blast radius) and the privileged binding *still* needs seeding by something (recursion not escaped); **Gardener-native elevated access** (`shoots/adminkubeconfig` or a Gardener-seeded privileged SA) — rejected for v1: `shoots/adminkubeconfig` is designed for humans/external tools not in-cluster controllers, and it couples the operator to Gardener internals (revisit only if the bootstrap MR proves burdensome); **grant the operator SA broad rights with no bootstrap MR** — impossible: that grant is exactly what cannot be self-applied.
- Applies to the wrapper-chart migration (the bootstrap MR lives in the much-smaller wrapper chart) and to `cluster-clients` (the operator SA must be pre-empowered for the shoot apply to succeed). Not implemented by this change's operator code; it is an install-time prerequisite the operator depends on.
- Install RBAC differs by **provisioning mechanism, not by breadth** — both appliers are broad; only *who seeds the grant* differs. (Corrected from an earlier "host = namespaced Role only" framing after chart research disproved it — see below.)
  - **Host (seed):** provisioned by the operator's **own install chart**. The host render is **not** guaranteed namespace-local: chart research confirmed the candidate wrapper charts emit cluster-scoped resources on the host side (metal-operator and ipam-capi each ship a host-side `ClusterRole` + `ClusterRoleBinding` for their webhook-injector SA), and the operator's own `patch`/rename transforms can produce `ClusterRole`s. So the host grant must cover the host render's cluster-scoped kinds too, and where the host render creates RBAC it must itself hold those powers (privilege-escalation prevention). Scope it no broader than the host render needs (its kinds — namespaced *and* cluster-scoped — plus the `remoteAccess` Secret read and the leader-election Lease); set ownerReferences for GC. A "namespaced Role only" grant would be an invention the real charts violate.
  - **Remote (shoot):** the same broad, escalation-capable shape (CRDs, ClusterRoles/Bindings, Roles/Bindings, ServiceAccounts, Validating/Mutating WebhookConfigurations, + additions), but seeded by the **bootstrap MR (GRM)** rather than by the operator's own chart, because the shoot SA cannot grant itself RBAC (recursion — per above).
  - **Aligned to the reference appliers, not invented:** gardener-resource-manager grants its target-cluster applier a broad `cluster-admin`-equivalent `ClusterRole` (wildcard `*`/`*`/`*`, bootstrapped by a 10-min `system:masters` cert then a shoot-access token — exactly our remote side); Flux ships its appliers bound to `cluster-admin` and scopes tenants via **per-object ServiceAccount impersonation** (`spec.serviceAccountName`), explicitly *not* by narrowing the applier SA, because a narrowed applier cannot manage the CRDs/ClusterRoles/webhooks real renders contain. Both keep the applier broad by design.
   - The point: **both grants are broad applier grants; they differ only in provisioning — host is chart-provisioned, remote is GRM-bootstrapped.** Not the same delivery mechanism, but the same breadth.

**Decision: single operator-managed install per seed (host cluster-scoped objects use seed-global names)**
- Chosen: at most **one** `DualDeploymentOperator`-managed install of a given operator per seed. The host render's cluster-scoped objects (e.g. a `ClusterRole` / `ClusterRoleBinding`) keep their upstream **seed-global fixed names**; the operator does NOT auto-uniquify them per shoot-cp namespace. Deploying two CRs that emit the same-named cluster-scoped host object on one seed is an unsupported configuration.
- Reason: this matches how the current charts already behave, verified on live seeds `rt-qa-de-1` and `rt-eu-de-1` (via `u8s`): the host-side `ClusterRole`+`ClusterRoleBinding` (`metal-operator-webhook-injector`, `ipam-capi-remote-webhook-injector`) have static seed-global names with no `.Release.Namespace` qualifier, the `ClusterRoleBinding` carries a single subject in `{{ .Release.Namespace }}`, and each seed has two `shoot--cp--*` namespaces but runs the `-remote` operators in **only** the `m-<region>` workload namespace — never two at once. So the seed-global name never collides in practice; the current model is de-facto single-install-per-seed. The operator preserves this rather than inventing a uniquifier the upstream charts and their `roleRef`/subject references do not expect.
- Collision semantics if violated (why it's unsupported, not silently handled): two CRs emitting the same-named cluster-scoped object would (1) fight over SSA field ownership of one shared object, and (2) break prune/GC — a cluster-scoped object **cannot** be owner-referenced by a namespaced CR, so no per-CR owner-ref cascade exists and "which CR may delete it" is ambiguous (deleting CR A could remove a `ClusterRole` CR B still needs). Auto-uniquifying would also require rewriting every `roleRef`/subject reference to the new name consistently — machinery the upstream charts do not carry and that would diverge our render from upstream.
- Enforcement: documented as an install-time constraint (like the shoot RBAC bootstrap prerequisite), not runtime-validated in v1. A future enhancement MAY add a per-name uniquifier transform or an admission check that rejects a second conflicting install; out of scope here.
- Applies to `cluster-clients` (host grant) and the wrapper-chart migration. Not operator reconcile-loop code.
- Alternatives considered: **per-namespace name uniquifier** (append shoot-cp namespace / CR-derived suffix to host cluster-scoped names; fully multi-install-safe) — rejected for v1: upstream charts use fixed names and internal `roleRef`/subject references assume them, so the operator would have to rewrite object *and* references consistently, diverging from upstream for a case that does not occur in production; revisit if a seed ever needs two workload installs. **Shared seed-singleton objects with no per-CR GC** (apply last-writer-wins, exclude cluster-scoped host objects from prune/owner-ref) — rejected: still fragile if two CRs render *different* content for the same name, and leaks a stale `ClusterRole` after the last CR is gone.

**Decision: defensive cluster-scoped conflict guard (GET-before-apply, refuse to clobber a foreign-owned object)**
- Chosen: `SSAApplier.Apply` guards every **cluster-scoped** apply with a GET-before-apply check on the `dual-deployment-operator.cc.sap/owned-by` label. If the live object carries a *different* CR's identity, the applier refuses to apply it (no `ForceOwnership` clobber), records it `Health=Degraded` with a `Message` naming the conflicting owner, and surfaces a per-resource error (continue-on-error, requeue). Absent object, self-owned, or unlabeled → apply proceeds (unlabeled objects — e.g. pre-existing from the current Helm chart during migration — are adopted, gaining our label). Namespaced applies skip the guard (namespace isolation already prevents collision).
- Reason: single-install-per-seed is a documented *contract*, but a contract with no enforcement fails silently. Our applier uses `client.ForceOwnership` (needed to reclaim genuinely stale field managers), which would otherwise let two CRs on one seed silently ping-pong ownership of a same-named cluster-scoped object — last-writer-wins corruption with nothing surfaced. The guard reuses the `owned-by` label already stamped for prune safety, so the only added cost is one GET per cluster-scoped host object; it converts silent corruption into a visible, non-destructive failure. `ForceOwnership` alone cannot distinguish "reclaim my own stale field" from "steal another CR's object" — the label check supplies that distinction.
- Unlabeled-object semantics: an existing cluster-scoped object with *no* `owned-by` label is owned by no operator-managed CR (e.g. left by the current chart during migration), so it is safe to adopt — the plain apply proceeds and stamps our label. "Conflict" is specifically *another CR's* label, never merely "already exists".
- Applies to `resource-delivery` (the guard + the `owned-by` label requirement) and `reconcile-loop` (the `HostClusterScopedConflict`/`Degraded` surfacing via continue-on-error). Cluster-scoped-only keeps the extra GET off the common namespaced path.
- Alternatives considered: **document-only, no runtime guard** — rejected: a contract violation stays silent and corrupts the shared object; least defensive. **Adopt-with-ceremony for unlabeled objects** (explicit adopt step) — rejected as over-engineered: a plain apply already adopts an unlabeled object correctly by stamping the label; no separate ceremony needed. **Drop `ForceOwnership`** to avoid clobbering — rejected: `ForceOwnership` is required for the legitimate stale-manager reclaim case; the targeted label guard is the precise fix, not disabling force globally.

## Risks / Trade-offs

- [Operator transiently owns `caBundle` → webhook outage window on next apply] → Leaf-only unconditional strip + a `managedFields` discriminating test written RED-first; strip runs before every apply including the first.
- [Bootstrap gap: between operator's first apply (caBundle absent) and the injector's first patch, webhooks have no caBundle] → This is startup latency, not downtime (the webhook was never serving before); accepted per `docs/design.md` §3.8 bootstrap sequence. The operator does not report on caBundle in health, so the WebhookConfig reports `Healthy` (it exists; operator-owned fields applied) throughout — caBundle population is the injector's concern, not the operator's health signal.
- [Removing the finalizer before remote cleanup completes → orphaned shoot resources] → Keep the finalizer until remote deletion is confirmed complete (deleted or NotFound). On a **reachable** shoot with failing deletes, keep it and requeue. On an **unreachable** shoot, do NOT remove the finalizer and do NOT assume the resources are gone — "unreachable" is indistinguishable from "transiently down"; surface a `ShootUnreachable` condition + Event and requeue, keeping the CR in `Terminating` until the shoot returns or an operator manually removes the finalizer. Never silently orphan by guessing "gone".
- [Pruning a CRD cascades to all its CRs cluster-wide] → Prune/CR-deletion never deletes a CRD under the default `retentionPolicy.crds=Retain`; only explicit `Delete` allows it.
- [A chart bump that narrows a CRD schema (field made required, type narrowed) leaves existing CR instances silently non-conformant] → Inherent Kubernetes CRD-versioning hazard, not operator-detectable: the SSA apply succeeds (API server validates the schema definition, not stored objects) and `crdHealth` reports Healthy since `Established` stays True. The operator never migrates or rewrites CRs — backward-compatible schema evolution (via a conversion strategy) is the chart author's contract. Not a regression vs. the tools we replace: neither Helm nor kustomize protects against this either — Helm `crds/` never upgrades an existing CRD at all (arguably worse: a silent no-op "time bomb"; [helm docs](https://helm.sh/docs/chart_best_practices/custom_resource_definitions/)); Helm `templates/` and kustomize apply the new CRD with no CR-level validation/migration (kustomize is a stateless client-side generator with no stored-object awareness). Documented in `docs/design.md` so implementers do not assume every CRD apply implies CR-level compatibility.
- [A chart bump that removes an in-use storage version could orphan/lose stored CRs] → The API server rejects the CRD apply (`cannot remove version … listed in status.storedVersions`); the operator records that resource `Degraded` + the API error and requeues (continue-on-error). The bad update never lands, so existing CRs are preserved; the failure is surfaced in status rather than silently forced.
- [GET-after-apply doubles API calls per resource per reconcile] → Accepted for correct health; 10-minute requeue keeps steady-state call volume low; GET failure degrades to `Unknown` rather than erroring.
- [strategic-merge vs JSON-merge mis-selection (prior-change regression)] → Not re-litigated here (transformations shipped), but the delivery apply uses plain SSA `client.Apply`; the discriminating-test discipline is carried into the caBundle-strip test.
- [Operator SA cannot create shoot RBAC → applies fail with forbidden/privilege-escalation errors] → The operator's token-requestor SA holds only runtime domain perms and cannot create ClusterRoles/Bindings/SAs. A minimal, static bootstrap `ManagedResource` (applied by the already-privileged GRM) seeds the SA + an apply-scoped ClusterRole/Binding **before** the operator runs; this is a one-time install-time prerequisite, not part of the runtime delivery path (which stays GRM-free). If it is absent, the operator's remote applies fail — surfaced per-resource as `Degraded` (continue-on-error), not silently.
- [Two CRs on one seed emit the same-named host cluster-scoped object → collision] → Host cluster-scoped objects (e.g. `ClusterRole`/`ClusterRoleBinding`) use upstream seed-global fixed names, not per-namespace-qualified ones. Two operator-managed installs on one seed emitting the same-named object would fight over SSA field ownership and have ambiguous prune/GC (a cluster-scoped object cannot be owner-referenced by a namespaced CR). Mitigated by the single-install-per-seed constraint (documented install-time contract, matching current production reality on `rt-qa-de-1`/`rt-eu-de-1` where the `-remote` operators run in only the `m-<region>` workload namespace). Not runtime-validated in v1; a per-name uniquifier or admission guard is a possible future enhancement. See the "single operator-managed install per seed" Decision.
- [Single-install-per-seed contract violated at runtime → silent last-writer-wins corruption of a shared cluster-scoped object] → Even with the contract documented, a misconfiguration could deploy two CRs whose host renders emit the same-named cluster-scoped object. Because the applier uses `ForceOwnership`, this would silently ping-pong ownership. Defended by the cluster-scoped conflict guard: a GET-before-apply checks the `dual-deployment-operator.cc.sap/owned-by` label and, on a *different* CR's identity, refuses to apply (no clobber), records the resource `Degraded` naming the conflicting owner, and requeues (continue-on-error). Turns silent corruption into a visible, non-destructive failure. Unlabeled pre-existing objects (e.g. from the current chart during migration) are adopted, not refused. See the "defensive cluster-scoped conflict guard" Decision.

## Migration Plan

Deployment steps:
1. Add `spec.applyOrder` and rename `spec.deletionPolicy` → `spec.retentionPolicy` (type `DeletionPolicy` → `RetentionPolicy`, keep `.crds`) in the CRD types; run `make manifests generate`.
2. Implement `internal/clients` and `internal/deliver` (TDD, per-task).
3. Replace the no-op reconciler with the full loop; wire the host applier at manager startup.
4. `make lint-fix && make test`; then envtest integration (dual API-server harness for the shoot).
5. Deploy per-shoot; verify host + remote resources apply, status populates, `Ready` reaches `True` once the injector stamps caBundle.

**Prerequisite (install-time, not operator code):** a minimal per-operator bootstrap `ManagedResource` — applied by GRM (privileged) — must seed the shoot ServiceAccount the operator authenticates as, plus an apply-scoped ClusterRole/Binding (create/update/delete on CRDs, RBAC, ServiceAccounts, WebhookConfigurations, and additions). Without it the operator's SA cannot create shoot RBAC (privilege-escalation prevention) and remote applies fail. See the "shoot RBAC bootstrap" Decision.

Rollback:
- The reconciler is additive over a no-op; reverting to the prior commit restores the no-op stub. Applied resources are not garbage-collected on operator downgrade (no ownerRef cascade across clusters); a `spec.applyOrder`-aware CR deletion is the supported teardown path.
